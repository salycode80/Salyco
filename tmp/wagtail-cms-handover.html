Wagtail Article CMS

Articles are Django-rendered pages with their content in the first response, edited in a Wagtail admin at /cms/. Everything else on the site is untouched: the catalogue, cart, warranty and account surfaces stay on the existing DRF API and the React SPA.

01

Architecture implemented shipped

Wagtail is installed inside the existing Django project and owns one content type: articles. It is a CMS for the blog, not a rebuild of the website.

  • /cms/ — the editorial admin. /admin/ — the original Django admin, unchanged.
  • /articles/… — Django renders the pages. No JavaScript is needed to read an article.
  • The React SPA keeps every other surface and reaches the API exactly as before.
  • wagtail.urls is mounted last, after the explicit routes, as a fallback — with a bare-path guard so / 404s instead of resolving Wagtail's own root.

The Product model was not duplicated, no existing route was moved, and the legacy article table was not deleted.

02

Wagtail version, and why this one

7.4.3, pinned exactly in requirements.txt.

An unpinned wagtail>=7.4 resolves to 8.0, which requires djangorestframework>=3.18 — and that would force an upgrade of the DRF underneath every existing endpoint in the project. 7.4.x is the LTS line, supported to 2027-11-02, and needs only DRF>=3.15.1, which the installed 3.17.1 satisfies. It runs on the Django and Python already in place.

06

Existing article migration strategy

Additive, never destructive. The legacy articles.Article table, its rows and its Django admin all stay in place, so the old content remains readable and re-exportable no matter what happens next.

migrate_legacy_articles converts each row into a live ArticlePage:

  • the stored text is parsed into paragraphs and headings;
  • publication state and the original date are carried across;
  • a permanent 301 is written from the old slug to the new URL;
  • an article whose conversion comes out shorter than the original is aborted, so a parsing bug cannot silently truncate someone's writing.

It is idempotent — a second run updates rather than duplicating — and --dry-run reports everything it would do while writing nothing.

Nginx changes

New locations in Frontend/salyco-front/nginx.conf:

LocationWhy
= /articles301s to /articles/ rather than proxying an empty remainder
^~ /articles/The server-rendered article pages
^~ /cms/The editorial admin
^~ /documents/Wagtail's document handler — without it these fall through to the SPA and return index.html with the wrong content type
= /sitemap.xml, = /robots.txtExact matches, so a future /sitemap-images.xml is not swallowed

^~ keeps the image-negotiation regex from intercepting them. /static/ and /media/ already existed and are unchanged.

11

Environment and config changes

  • INSTALLED_APPS — Wagtail and the apps it needs, plus django.contrib.sites. wagtail.contrib.forms is deliberately absent; the project has no Wagtail form pages.
  • MIDDLEWARE — Wagtail's redirect middleware, which is what makes an old slug 301 to a new one.
  • SITE_ID = 1.
  • SITE_URL — read from the environment, defaulting to https://salyco.ir. Every canonical, OG tag, JSON-LD URL and sitemap entry derives from it, never from the request, because three proxies stand between Django and the client and one wrong X-Forwarded-* header would otherwise leak http://backend:8000/… into the metadata.
  • WAGTAIL_SITE_NAME, WAGTAILADMIN_BASE_URL, WAGTAIL_ENABLE_UPDATE_CHECK = False.
  • requirements.txt — wagtail==7.4.3.
  • vite.config.js — the dev proxy now mirrors the nginx locations.

No new environment variables are required — SITE_URL has a working default.

12

Roles and permissions

None were invented. Access to /cms/ is Wagtail's own model:

  • migrate runs Wagtail's 0001_create_admin_access_permissions, which creates the Moderators and Editors groups and the admin-access permission.
  • A user needs wagtailadmin.access_admin to reach /cms/; superusers have it implicitly.
  • setup_salyco_cms creates no users and no groups — it only creates the site, index, collections and SEO settings.

To give an editor access: Settings → Groups in the CMS, or Django admin at /admin/. To create the first account, run createsuperuser (item 15).

Local database note: Backend/db.sqlite3 holds a single superuser, 09933921096. Its password is hashed and cannot be read back — reset it with changepassword if it is not known. There is also a leftover staff account, probe-admin, with an unusable password; it can be deleted.

Remaining manual deployment steps deploy-time

These cannot be done from a development machine and are the only work still outstanding:

  1. Run the deploy block above, then check the four responses: 
    curl -sI https://salyco.ir/articles/ | head -3
curl -s  https://salyco.ir/robots.txt | head -3
curl -s  https://salyco.ir/sitemap.xml | head -5
curl -sI https://salyco.ir/articles/<legacy-slug>/ | grep -i location

    Expect 200 text/html from Django — not the SPA shell — text/plain for robots, XML whose URLs all read https://salyco.ir/ with no local host, and a 301.

  2. Paste an article URL into Telegram and confirm the card shows the title, description and image. This one is genuinely untestable anywhere but production.
  3. Confirm nginx serves the pages, not the SPA. If /articles/ returns the React shell, the location block did not take effect.
  4. Rehearse the rollback once: comment out the four locations, rebuild the frontend, and confirm the site still runs. Articles then 404 rather than serving stale React pages — that is the expected degraded state. Restore and rebuild. The legacy table and its Django admin are still there throughout, so nothing is lost either way.
—

Four things worth knowing

Changing a slug already redirects

Wagtail writes a permanent 301 automatically when a live page's slug changes — verified, one hop, no follow-up needed. (The implementation plan predicted a 404 here and was wrong; it has been corrected.) Note it does not update other pages that link to the old URL.

A paginated index canonicalises to page one

/articles/?page=2 emits the canonical of /articles/, because the canonical is built from the page path and carries no query string. Nothing breaks — every article is in the sitemap and page 2 is linked from page 1 — but Google's guidance prefers a paginated series to canonicalise to itself. This is a product decision, not a bug, so it was recorded rather than patched.

localhost:8000/articles/ looks unthemed, and that is not a defect

Django serves the markup and the article stylesheet, but /tokens.css and the logo live in the frontend's public/ and are served by nginx from the SPA build root — never by Django. Running Django alone, the page keeps its layout and loses its whole palette. Port 8000 is not a supported surface for article pages; view them through :5173 (the Vite dev server, which now proxies the CMS routes) or through a proxy that reproduces the nginx split.

What was verified by watching, and what was not

Six widths from 360 to 1440px were driven in a real browser: no horizontal scroll anywhere, a 640px measure above 672px, the FAQ opening without JavaScript, and Latin text isolated correctly inside Persian prose. The CMS was driven end to end through its own forms — create, every block type, publish, edit. The API, the redirects, the sitemap and the metadata were all checked against a running server.

One step was reasoned about from source rather than driven, and a real bug slipped through exactly there: vite.config.js did not proxy /articles, so the article pages were unreachable from the dev server. That is fixed and re-verified, and the plan now records it as the lesson it is.
