{% comment %} The site header, server-rendered — two headers, actually, one per breakpoint. Both are in the HTML on every page; a media query in article.css shows one and hides the other. That is why the partials this includes (site_search, site_nav) are shared rather than copied, and why the search form takes a `uid`: hiding an element with CSS leaves it in the document, so a fixed id would collide. This mirrors the React chrome rather than the desktop header alone. Above 1024px it is Navbar.jsx — white surface, subtle bottom hairline, a top row with the logo leading and the account and cart controls trailing, then a 44px centred link row (§8). Below 1024px it is MobileTopBar.jsx: a single 68px row with the brand on the right and the account control and a menu toggle on the left. Measured before: stacking the desktop header on a 360px phone made it 242px tall — a quarter of the screen before the reader reached the title, with the six links wrapped onto three rows. §8 asks for a compact mobile menu and a search with room to breathe; this is that, and nothing shrinks to get there. What it deliberately does NOT duplicate is state, and here that is a hard constraint rather than a preference. The React header shows the signed-in phone number and a live cart count. Neither is knowable on this side: the SPA authenticates with a JWT kept in localStorage, which only its own JavaScript attaches as an Authorization header, so a plain navigation to /articles/... arrives carrying no credentials and request.user is always AnonymousUser. request.user would be worse than useless here, which is why nothing in these templates reads it. AuthenticationMiddleware populates it from a Django session — on this site that means an /admin/ editorial login, not a shop account. Wiring the header to it would name the editor and show nothing to every customer: accidentally plausible, and wrong. That is also why the account link reads «حساب کاربری» and not «ورود به حساب کاربری». The longer wording is a claim about the reader — it says they are not signed in — and for a signed-in reader that claim is false, because this page cannot see that they are. The short form names a destination instead, and a destination is true either way. It matches MobileTopBar.jsx as well, so the desktop and mobile bars agree. Showing the real number would mean the SPA mirroring display-only state into a cookie this half could read — a mechanism worth building only if the drift is worth it. The cart count is absent for the same reason, and absent rather than guessed: a hardcoded "0" would be a lie, an empty space is only an absence. The mobile menu is a
, not a script: these pages ship no JavaScript. It is hidden with an explicit rule rather than relying on the UA stylesheet to collapse it, because any author `display` on the panel would otherwise win and leave the menu permanently open. Cart lives in the panel because the compact row has no room for it and there is no tab bar on these pages — without it the cart would be unreachable on a phone except through the footer. {% endcomment %}
